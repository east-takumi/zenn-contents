# AWS Healthとは？

AWS Healthは、AWSのサービスやリソースに関する変更を確認できるサービスです。
AWS Health Eventを通して、それらの変更が自分たちのアプリケーションにどう影響するかを確認できます。

AWS自体の障害だけでなく、サービスのアップデートやEOL、メンテナンスなども確認する対象になります。
今回は、そのイベント情報とイベントに紐づくリソースをAWS Health APIから取得して扱います。

# 通知は来るけど、確認が追いつかない

某プロジェクトでは、AWS Chatbot経由でSlackにHealth Eventを通知していました。
対象はDev / Fut / Stg / Prdの4環境です。Organizationsの管理アカウントにはアクセスできない状況でした。

通知からわかるのは、どの環境でどのイベントが来たか、というところまで。
AWS自体の障害の通知もありますが、多くはEOLやサービスのアップデートに関するものでした。

同じような通知が4環境から来るうえに、Slackではほかのメッセージに流されてしまいます。
スレッド内に通知が来ることもあり、追いかけるのが大変でした。

さらに、通知を見ただけでは対応が必要なのか判断しにくいんですよね。

* 影響を受けるリソースは、都度コンソールで確認する必要がある
* PBI（JIRAチケット）と紐づいていないので、対応状況がわからない
* Miroの付箋で管理しているが、付箋を消したあとに対応不要と判断したものかどうかわからなくなる

毎朝この確認をするより、もっと重要なことに時間を使いたい。
そこで、APIでイベントを取得し、すでに対応中かどうかを判定して、新規分だけを毎朝通知できないかと考えました。

# 今回はイベントと対象リソースの仕分けまで

最終的には朝会で確認する情報を絞りたいのですが、まずはCLIベースで次の処理をするところをMVPとしました。

1. カテゴリとステータスを指定してHealth Eventを取得する
2. 取得したイベントに紐づくリソースを、ステータスで絞って取得する
3. 取得した情報をまとめ、対象リソース数を算出する

イベント自体のステータスと、リソースのステータスは別なので、ここを分けて見ていきます。

## 取得するイベントを絞る

資料で取り上げたイベントカテゴリは次の3つです。

| カテゴリ | 内容の例 |
| --- | --- |
| `issue` | AWS側のリージョン障害やサービスへの影響 |
| `scheduledChange` | EC2インスタンスのEOL、RDSのメンテナンスなど |
| `accountNotification` | アカウント固有のお知らせ、ACMの更新など |

このうち、今回は `scheduledChange` と `accountNotification` を対象にしました。
イベントのステータスは `open` と `upcoming` に絞っています。

これは今回のMVPで扱う範囲です。`issue` のイベントを対応不要と判断しているわけではありません。

## イベントに紐づくリソースを絞る

次に、取得したイベントに紐づくリソースを取得します。
リソース側にはAffectedEntityのステータスがあり、資料では次のように整理しました。

| ステータス | 状態 |
| --- | --- |
| `IMPAIRED` | 影響が出ている・影響を受けている |
| `UNIMPAIRED` | イベントに紐づいているが、現時点では影響がない |
| `UNKNOWN` | 状況が不明 |
| `PENDING` | 影響や対応などが保留、または今後発生する予定 |
| `RESOLVED` | 解決済み |

今回は `RESOLVED` を除いた4つを取得対象にしました。
現時点で影響が出ている `IMPAIRED` だけでなく、`UNIMPAIRED` や `UNKNOWN`、`PENDING` も含めて確認する形です。

このため、集計する対象リソース数は、今まさに障害が起きているリソースの数とは限りません。
指定した条件に当てはまるリソースをまとめて数えています。

# ここから先にやりたいこと

今回できたのは、Health Eventを仕分けし、対象リソース数をCLIで算出するところまでです。
対応状況の判定や差分通知まで進めるには、まだ考えることがあります。

## JIRAチケットとの突合

イベントを取得できても、それだけではチームがすでに対応しているかどうかはわかりません。
Health EventとJIRAチケットを何で紐づけるかを決める必要があります。

Health Event側では `eventTypeCode`、サービス名、リソースIDなどが候補です。
JIRA側ではラベルやカスタムフィールドに対応するイベントの情報を持たせることを考えていますが、何を突合キーにするかは今後の検討です。

## 差分通知の自動化と4環境の集約

毎朝の通知にはLambda + EventBridge Schedulerなどを考えています。
Step Functionsでもできそうなので、このあたりも検討したいところです。

あわせて、4環境分の情報を1箇所に集約する仕組みも必要になります。
ここまでできれば、すでに対応中のものと新しく確認するものを分けて、朝会で見る情報を絞れそうです。

# まとめ

今回はAWS Health APIを使って、イベントと対象リソースを仕分けするところまでを紹介しました。
通知の確認から対応状況の管理までを自動化するには、JIRAとの紐づけや差分通知の仕組みがまだ必要です。
